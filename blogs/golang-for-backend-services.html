Golang for backend services: what changes coming from Node.js

Most of my career has been split between Node.js dashboards and Go services sitting behind them. The switch isn't about performance first — Node is plenty fast for the vast majority of API workloads. It's about what the language forces you to make explicit.

Goroutines instead of callbacks

In Node, concurrency is a single-threaded event loop with callbacks, promises, or async/await layered on top. It works well until you need real parallelism — CPU-bound work, or fan-out across dozens of downstream calls with independent failure handling. Go's goroutines are cheap enough that you reach for concurrency by default, not as a special case:

func fetchAll(ids []string) []Result {
    results := make([]Result, len(ids))
    var wg sync.WaitGroup
    for i, id := range ids {
        wg.Add(1)
        go func(i int, id string) {
            defer wg.Done()
            results[i] = fetch(id)
        }(i, id)
    }
    wg.Wait()
    return results
}

No thread pool to configure, no worker library to pull in. That's the pitch: concurrency primitives that are part of the language, not a framework decision.

Errors are values, not exceptions

Go makes you handle every error at the call site — if err != nil shows up constantly, and it's genuinely annoying at first. The upside only becomes obvious later: you can't accidentally swallow an error three layers up in a try/catch that was scoped too broadly. Every failure path is visible in the function signature. For services that talk to flaky devices or third-party APIs, that discipline pays for itself.

The standard library gets you further than you'd expect

net/http, encoding/json, and context cover most of what a typical Node project pulls in five or six packages for. Fewer dependencies means fewer supply-chain surprises and a smaller mental model for anyone joining the codebase — which matters more than it sounds once a service has been running in production for a year.

None of this makes Go a universal upgrade. I still reach for Node/Next.js for anything dashboard-shaped, where the ecosystem and iteration speed win. But for protocol brokers, event bridges, and anything that needs to hold hundreds of long-lived connections without falling over, Go has earned the default slot.
