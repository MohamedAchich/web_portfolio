Structuring a NestJS API that survives real traffic

NestJS gets criticized for being "too Java" — decorators everywhere, modules, providers, a dependency injection container. The criticism is fair if you use all of it for a CRUD API that Express would have handled in 200 lines. It stops being fair the moment you have auth, rate limiting, background jobs, and three teams touching the same service.

Modules as boundaries, not folders

The mistake I see most often is treating Nest modules as a directory-organization tool — UsersModule, OrdersModule, one per database table. That's just Express with extra ceremony. Modules earn their keep when they enforce a real boundary: a module only exports what other modules are allowed to depend on, and everything else stays private. That's the difference between "organized" and "actually decoupled."

Guards and interceptors instead of middleware soup

Express middleware is a flat pipeline — auth, logging, and validation all live in the same conceptual layer, and ordering bugs are easy to introduce. Nest splits that into guards (can this request proceed at all), interceptors (transform the request/response), and pipes (validate and coerce input). Once a team internalizes which one to reach for, request handling stops being a grep through fifteen app.use() calls:

@UseGuards(OrgScopedGuard)
@UseInterceptors(AuditLogInterceptor)
@Post(':orgId/devices')
createDevice(@Param('orgId') orgId: string, @Body() dto: CreateDeviceDto) {
  return this.devices.create(orgId, dto);
}

Where Express still wins

For a single-purpose service — a webhook receiver, a small internal tool — Express with a couple of well-chosen middlewares is still faster to write and easier for a new hire to read in one sitting. Nest's payoff shows up on the timeline where a service outlives its first author, gains a second team, and needs auth and observability to be structural rather than bolted on. Pick based on which problem you actually have, not which one is trendier this year.
